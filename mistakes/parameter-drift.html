1.1The finished task drifts from its assigned parameters

Fails the taskHard Client Requirements · Task parameters are mandatory

The mistake

The finished task quietly swaps out part of its assignment: an assigned tool the prompt rules out, an Execution target turned into a local file, a scenario reworked into a different situation.

Do this instead

Check the prompt, the inputs and the rubric against every assigned parameter. Name the step each assigned tool is necessary for, and put the deliverable where the Execution target says it ends up.

Where it happened

2 real Green Shell tasks. Each shows the spot and what it should have been; click any line to open the task there.

Example 1Shopping · Hunting best deals & bargaining · single turn

What is wrongThe task is assigned one tool, the browser, and the capability use_latest_info, yet the prompt tells the agent to stay off the web. Every price it can reach comes from the user's own notes or draft page.

A Raleigh student wants the Wacom tablet from a Best Buy shelf tag cheaper online. The prompt hands over four notebook photos and asks for wacom_price_check.html.

Where it shows

Prompt
Don't go looking stuff up on the web, prices move around, the listings I care about are the ones in my notes.
Assigned tools
browserthe only tool the task is assigned
Secondary capabilities
apply_external_rule, use_latest_info, filter_out_of_scope, compute_answer
Scenario
Find me the same unit cheaper online, but only count sellers that ship to Raleigh, have stock today, and are the retailer themselves rather than a marketplace seller.

What it should have been

Prompt
What I want to know is if I can get the exact same unit cheaper online right now, but I only want to count sellers that ship to my place in Raleigh…the web ban gone: the browser is the tool this task is assigned
Objective criteria
Prices graded as the run retrieves them, the figure written as an example only: Walmart.com's delivered price, based on the price retrieved during the run (e.g., $72.93).

The shelf tag photographed in the store, as the scenario assigns.

How it breaks the standardThe browser is the one tool this task is assigned and use_latest_info one of its capabilities; the prompt rules both out, so the correct final state rests on prices the user copied by hand. The scenario's goal, finding the unit cheaper online, becomes a comparison of listings already written down.

The rule it breaksGuidelines · Hard Client Requirements for Every Task Omitting, substituting, or drifting from any assigned parameter makes the task invalid and subject to automatic rejection. The scenario also changes: online search becomes reading notes.

Example 2SMB · Running business operations · single turn

What is wrongThe Execution target is drafts in the mail client, none sent. The prompt moves the drafts into a markdown file instead, and no criterion checks a draft in the mail client.

A print shop owner audits Yolanda's delivery notes against her digital records, and wants an interactive control page plus the August invoices drafted.

Where it shows

Execution target
Drafts created in the mail client, none sent, plus the dashboard written to file storage
Prompt
Save all consolidated drafts in a file named draft_invoice.md
Objective criteria
No criterion checks a draft in the mail client. Criterion 22 only penalises sending; criteria 10 to 16 grade the file.

What it should have been

Prompt
…draft an invoice email to each client's contact and leave them in my drafts, please do not send anything yet.
Objective criteria
A State Change criterion per draft, such as: a Gmail draft to Domenic Kelleher (dkelleher@kellehersteel.com) bills a corrected total of $1,087.50. Criterion 22 already penalises sending.

How it breaks the standardThe Execution target says where the deliverable ends up, and the Guidelines make it binding. Moving the drafts into a markdown file removes the state change the client assigned, and nothing in the rubric can tell whether a draft ever reached the mail client.

The rule it breaksGuidelines · 1.1.2 Rest of the Parameters Where the deliverable ends up and any limit on the run, such as nothing sent. State both in the prompt, or they cannot be graded. The verification condition checks that each draft is addressed from contacts and that nothing is in Sent.

Catch it in your own task

Read the parameter row next to your prompt. For each assigned tool, point at the sentence that makes it necessary; for the Execution target, point at the criterion that grades it. Anything you cannot point at has drifted.

Where the correct guidance is written

Section titles as they print, so you can search for them in the document.

Guidelines · Hard Client Requirements for Every Task

These are binding client requirements, not suggestions. Omitting, substituting, or drifting from any assigned parameter makes the task invalid and subject to automatic rejection.

Exceptions should be rare: a parameter the universe genuinely cannot support, or a setup too simple to produce the required failure.

Guidelines · 1.1.2 Rest of the Parameters

The services the task is built around. Confirm they are loaded, then make the correct final state depend on them, not on whichever service is easiest to reach.

QC spec · Task Parameters - Scenario Adherence

The task is not built on the assigned scenario: it changes the user, the goal or the deliverable, or reduces the scenario to a passing mention.

The failing option, Fail - Scenario Not Followed.

Why it matters

The fourteen parameters are binding client requirements. Omitting, substituting or drifting from any one of them makes the task invalid and subject to automatic rejection, however good the rest of it is. A deviation is allowed only where the universe genuinely cannot support a parameter or the setup is too simple to produce the required failure, and then only as far as strictly necessary.
